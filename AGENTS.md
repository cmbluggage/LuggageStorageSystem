# Stowaway — Architecture & Engineering Guidelines

Stowaway is a luggage storage/rental booking platform (Sri Lanka, prices shown USD + LKR). Built with Next.js 16 (App Router), React 19, Tailwind CSS v4, TypeScript, and Supabase (Postgres + Auth). No test suite currently exists — verify changes manually in the browser (`npm run dev`) and with `npm run lint`.

## Design System (Orange & Dark Brown)
- **Primary Accent**: Vibrant Orange (`#EA580C` design tokens / `#e8620a` Figma header+pricing accent / `bg-orange-600`). Used for main action CTAs, active pills, highlights, and primary buttons.
- **Dark Surface**: Rich Dark Brown (`#1C130E`). Used for dark bands, dark footers, text headings, and dark promo containers.
- **Card Geometry**: Soft rounded 16px cards (`rounded-2xl`), circular 40px quantity steppers (`rounded-full`), and custom popover dropdowns.
- **No Native Controls**: Never use native `<select>` or native `<input type="date">`. Always use `CustomSelect` (`src/components/ui/CustomSelect.tsx`) and `CustomDatePicker` (`src/components/ui/CustomDatePicker.tsx`).
- **Typography**: Plus Jakarta Sans is the site-wide default font (`--font-site` in `globals.css`), loaded in `layout.tsx`. It applies everywhere except inside `.admin-shell` (the root wrapper class on `/admin` and `/staff`), which keeps Google Sans (`--font-google-sans`) — those are internal dashboards, not part of the customer-facing brand. `.font-mono-ibm` opts into IBM Plex Mono for accent text (e.g. the pricing table's "PRICING" eyebrow).
- **Header**: One shared header — `src/components/ui/SiteHeader.tsx` — used by the landing page and every customer-facing page (`/book`, `/login`, `/my-bookings`, `/checkout/[id]`, `/booking/[id]`, `/booking/[id]/confirmation`). `variant="landing"` uses in-page `#hash` links; `variant="page"` (default) links to `/#hash`. On mobile (`<sm`) it shows the logo mark only, no wordmark. There is no separate `NavBar` component anymore — it was deleted when unified into `SiteHeader`.
- Shared primitives live in `src/components/ui/` (`Button`, `Card`, `SiteHeader`, `PillTag`, `Toast`, `SmoothScroll`); booking-flow-specific pieces live in `src/components/booking/`; admin primitives in `src/components/admin/`.
- **Smooth scroll**: `lenis` is mounted once via `SmoothScroll.tsx` in the root layout; it no-ops under `prefers-reduced-motion: reduce`. `globals.css` has the corresponding `html.lenis` rules — don't reintroduce `scroll-behavior: smooth` on `html`, it fights Lenis.
- **SEO**: `src/app/sitemap.ts` and `src/app/robots.ts` (Next.js file conventions) plus `src/lib/site.ts` (`SITE_URL`, reads `NEXT_PUBLIC_SITE_URL`, currently a placeholder domain — set the real env var once the production domain is live). Client-component routes (`/book`, `/my-bookings`, `/login`) get their `metadata` export from a sibling `layout.tsx` since a `'use client'` page file can't export `metadata` directly.
- **Hero decorative images**: `hero-airport.png`/`hero-luggage.png` are absolutely positioned full-bleed against the true viewport edges (`inset-0` on the section, not inside any `max-w`/grid wrapper — a max-w container there re-introduces dead space between the image and the browser edge). They show from `lg` (1024px) up, scaling from ~30% width at `lg` to the original Figma proportions (37.25%/39.08%) at `2xl`. Their bounding box does overlap the centered `max-w-[980px]` text column by design — the PNGs have transparent padding on their inner edge so the artwork itself doesn't visually clash with the text; don't "fix" that overlap by shrinking/hiding the images, that was already tried and reverted per user feedback (they want the images large and visible from `lg` up, matching the Figma reference).
- **`eval()` console warning in dev**: expected and harmless. `next.config.ts`'s CSP deliberately omits `unsafe-eval`; React's dev-mode debug tooling wants it and logs a warning, but never actually needs it in production. Do not add `unsafe-eval` to fix this.
- **Landing page content width/margins**: sections use `max-w-[1100px]` (was 1180) with responsive padding `px-6 md:px-10 lg:px-14 xl:px-20 2xl:px-28` (was `px-6 xl:px-0`) to match the Figma reference's generous side gutters at desktop widths. `SiteHeader` uses the exact same `max-w-[1100px]` + padding scale so the nav bar's edges line up pixel-for-pixel with the page content below it — keep these two in sync if either changes.
- **Services section icons**: the 6 cards under "Our Services" use real `lucide-react` icons (`Lock`, `CalendarClock`, `Clock`, `MapPinned`, `PlaneTakeoff`, `CreditCard`) inside the orange-tinted circle, with a hover animation (icon circle fills orange + scales, card lifts with a soft shadow). No rotate — tried it, looked bad, removed. If adding more service cards, give each a distinct icon rather than reusing a placeholder.
- **One toast system**: `notify` from `src/lib/toast.ts` (react-hot-toast, `<Toaster />` mounted once in root `layout.tsx`) is the only toast mechanism in the app. There used to be a second, parallel one — a hand-built `ToastContainer`/`onNotify` prop threaded through `admin/page.tsx` → `CatalogEditor`/`SettingsPanel`/`TimeSlotsPanel` — which fired alongside `notify` on every save, producing two success toasts for one action. That component and prop are gone; don't reintroduce a local toast queue anywhere, always call `notify.success`/`.error`/`.info` directly.

## Project Structure

### Pages (`src/app/`)
- `page.tsx`: Marketing Landing Page with Bounce-style Search Hero (`src/components/landing/LandingPage.tsx`).
- `book/page.tsx`: Dedicated 4-Step Booking Engine (Location -> Time -> Items -> Personal Info).
- `booking/[id]/page.tsx`: Single booking detail view.
- `booking/[id]/confirmation/page.tsx`: Booking Confirmation & QR Pass (uses `qrcode`).
- `my-bookings/page.tsx`: Customer Booking History & Support Dashboard (Direct Call & WhatsApp Team actions), looked up by phone number.
- `checkout/[bookingId]/page.tsx`: Final Checkout & Payment Simulation (cash vs. simulated Stripe).
- `admin/page.tsx`: SuperAdmin Control Panel. Nav is grouped by business function, not by table: **Day to day** (Bookings — the default landing tab — and Payments), **Pricing & Catalog** (Item Tiers, Add-on Services), **Locations & Schedule** (Locations, Operating Hours), **Business Rules** (Settings), **Records** (Audit Log). Keep new tabs in the group that matches what an operator is trying to do, not which table they touch.
- `staff/page.tsx`: Operations Dashboard — a single flat, time-ordered job queue (Uber-driver style, per explicit client feedback that the old Window/Type/Location filter row + four summary tiles was too much to configure before seeing your work). No filter toolbar; the server's location-grouped response is flattened and sorted by time client-side. Each job card always shows Call/WhatsApp/"Edit / Extend"/cash-collect/pay-link, plus one big primary action button (advance status) — "more details" is a separate, collapsed disclosure for the boring stuff (passport, insurance, line items), not where the actions live. Don't reintroduce a filter row here without client sign-off; that's the exact complexity that was deliberately removed.
- `login/page.tsx`: Portal Login for Staff & SuperAdmin (strictly accessed via `/login`; redirects unauthenticated users away from `/staff` and `/admin`). No longer has a "quick-fill seed credentials" panel — it used to hardcode the old `admin@stowaway.lk`/`staff@stowaway.lk` demo creds directly on the live login page, which is both wrong now (real accounts use different emails/passwords per deployment) and not something a client-facing production login screen should expose. Don't re-add a credentials shortcut here.

### API Routes (`src/app/api/`)
- `bookings/route.ts`:
  - `POST`: Creates a booking. Validates payload via Zod (`email` is now **required**, and `emailVerificationId` must reference a completed `booking_create` OTP verification — see the Email OTP section below), enforces IP rate limits and Turnstile bot protection, verifies operational limits and lead times from `app_settings`, recalculates pricing server-side from live DB rows (fails closed if DB is unreachable), and calls `saveBooking`.
  - `GET` (phone-only lookup) **removed** (2026-09) — see Email OTP Verification below for what replaced it and why.
- `my-bookings/route.ts` (`GET`, public, rate-limited): the customer booking-history endpoint, gated by a completed `booking_lookup` OTP verification (`?verificationId=...`). Replaces the old `GET /api/bookings?phone=...`.
- `otp/request/route.ts` (`POST`, public, rate-limited): sends a 6-digit email code. See Email OTP Verification below.
- `otp/verify/route.ts` (`POST`, public, rate-limited): checks a submitted code.
- `bookings/[id]/route.ts`: `GET` fetches a booking by id; `PATCH` sets the payment method preference (cash) or, when no live Stripe key is configured, instantly settles the dev-fallback card payment via `updateBookingPayment` (server enforces airport-cash lockout regardless of client payload — see Business Rules below). Once Stripe is configured, calling this with `stripe` throws — real card payments go through the checkout route below instead.
- `bookings/[id]/checkout/route.ts` (`POST`, public, rate-limited): creates a real Stripe Checkout Session for whatever the booking's ledger says is still owed (`balanceDueUsd`) — same call for a first payment, a post-extension top-up, or a partial-payment catch-up. Used by the customer checkout page and by staff's "Get pay link" action. 503s with a clear message if Stripe isn't configured yet.
- `stripe/webhook/route.ts` (`POST`, **not** behind `requireStaff` — authenticated by Stripe's signature instead): the only place a Stripe payment is actually marked settled. Reads the raw request body (signature is computed over the exact bytes). Idempotent against webhook retries.
- `staff/bookings/[id]/details/route.ts` (`PATCH`, `requireStaff`, rate-limited): edits a booking's customer name/email, flight number, notes, or drop-off/pick-up location+time via `updateBookingDetails` in `db.ts`. Item quantities are **not** editable through this endpoint — see Business Rules below for the re-pricing/balance-due behavior on a schedule edit. Sends a balance-due email (with a fresh Stripe pay link when configured) when the edit leaves a balance owing.
- `staff/bookings/[id]/collect-cash/route.ts` (`PATCH`, `requireStaff`, rate-limited): records a cash payment for the booking's current `balanceDueUsd` via `markCashCollected()`, then sends a payment-received email.
- `admin/payments/route.ts` (`GET`, `requireSuperAdmin`): paginated payments ledger plus today/week/all-time totals, backing the admin Payments panel.
- `locations/route.ts`, `item-tiers/route.ts`, `addons/route.ts`, `time-slots/route.ts`: Full catalog CRUD endpoints backed by `createCatalogHandlers` (`GET` is public or `?all=1` for admin; `POST`, `PATCH`, `DELETE` are protected by `requireSuperAdmin`).
- `admin/bookings/route.ts` (`GET`): Paginated booking browser for SuperAdmin with status, payment status, and search query filters.
- `admin/settings/route.ts` (`GET`): Returns full `app_settings` rows (types, labels, min/max bounds) for the SuperAdmin settings control panel.
- `settings/route.ts`:
  - `GET`: Serves safe public subset of dynamic settings and the Turnstile site key for the booking engine.
  - `PATCH`: SuperAdmin endpoint to update configuration with server-side validation against declared type and min/max bounds, with audit logging.
- `staff/operations/route.ts` (`GET`, rate-limited per staff user): Operations board endpoint flattening upcoming bookings into time-ordered drop-off and pick-up tasks grouped by location over a configurable rolling horizon window. When `?q=` is non-empty, it instead returns `{ searchResults }` from `searchAllBookings()` — any booking, any status/date — since the windowed task view can never surface a completed or historical booking.
- `staff/bookings/[id]/route.ts`:
  - `GET`: Fetches full booking details (including passport number) for staff.
  - `PATCH`: Advances or cancels booking status, enforcing valid state transitions (`ALLOWED_TRANSITIONS`) and logging to `public.audit_log`.
- `audit-log/route.ts` (`GET`): Reads `public.audit_log` with search and pagination for the admin panel.
- `exchange-rate/route.ts` (`GET`): Serves the live USD→LKR rate consumed by `src/lib/currency.ts`.

### Core Logic (`src/lib/`)
- `pricing.ts`: **Single source of truth** for duration and price calculations. Imported by both client components and server API routes — never re-implement duration/fee math elsewhere.
  - `calculateDuration`: bills in whole 24-hour cycles, `Math.ceil`, minimum 1 day (or configured `minBookingDays`).
  - `effectiveDailyRate`: bookings ≤ `weekThresholdDays` use `rate_daily_usd`; bookings > threshold use `rate_weekly_usd` applied to **all** days.
  - `calculateGrandTotal` = itemFee + dropoffSurcharge + pickupSurcharge + insuranceFee. No airport fee parameter — see Business Rules below.
- `db.ts`: Supabase data-access layer for bookings and payments (`saveBooking`, `updateBookingPayment`, `updateBookingDetails`, `updateBookingStatus`, `getBookingsByPhone`, `getBookingById`, `listBookings`, `searchAllBookings`, `getOperationalBookings`, plus the payments ledger: `recordPayment`, `markCashCollected`, `createPendingStripePayment`, `markStripePaymentSucceeded`, `markStripePaymentFailed`, `listPayments`, `getPaymentTotals`). All writes use the service-role client (`createAdminClient`) and fail closed on database errors (no unpersisted in-memory mocks).
- `settings.ts`: Dynamic business settings layer with in-memory caching and fallbacks to `DEFAULT_SETTINGS`.
- `locations.ts`: Location predicates and payment resolvers (`bookingTouchesAirport`, `isAirportLocation`, `resolvePayment`).
- `timeSlots.ts`: Time slot types (`window` = 2h block, `hourly` = 1h precision) plus `DEFAULT_TIME_SLOTS` and a `localStorage`-backed override (client-side only; server ignores it).
- `currency.ts`: USD↔LKR formatting; fetches the live rate client-side from `/api/exchange-rate` on load and caches it in a module-level variable (falls back to `NEXT_PUBLIC_USD_TO_LKR` env var, default 320).
- `auth/guard.ts`: Session and role enforcement (`requireStaff`, `requireSuperAdmin`, `getAuthActor`).
- `security/rateLimit.ts` & `security/turnstile.ts`: In-memory IP token bucket rate limiting and Cloudflare Turnstile token verification.
- `audit.ts`: `writeAudit` helper for writing audit records into `public.audit_log`.
- `api/http.ts` & `api/catalog.ts`: Standardized HTTP JSON response utilities (`ok`, `fail`, `badRequest`, `serverError`, `NO_STORE`) and generic CRUD handler generator.
- `stripe.ts`: Real Stripe Checkout Session + webhook-verification helpers, gated by `isStripeConfigured()` (checks `STRIPE_SECRET_KEY`, never simulated once configured). See Business Rules below.
- `email.ts` / `emailTemplates.ts`: Transactional email — Resend primary, plain SMTP (nodemailer) backup, every attempt logged to `public.email_log`. Real integration gated by configuration, not a simulation; see Business Rules below.
- `otp.ts`: Email OTP verification shared by booking creation and `/my-bookings`. See Email OTP Verification below.
- `validation/schemas.ts`: Central Zod schemas for all bookings, catalogs, status updates, settings, and query parameters.
- `supabase/admin.ts`: Service-role Supabase client factory for secure server-side operations bypassing RLS.
- `supabase/client.ts` / `supabase/server.ts`: Browser and server Supabase client factories.
- `supabase/types.ts`: Hand-maintained `Database` type mirroring the SQL schema — **keep in sync manually** when migrations change columns (not auto-generated).

### Middleware
- `src/proxy.ts` (Next's middleware entry point): Protects `/staff/:path*` and `/admin/:path*`. Validates the Supabase JWT locally via `getClaims()` (no network round-trip), redirects unauthenticated users to `/login`, and redirects non-`superadmin` roles away from `/admin` to `/staff`. Role resolution order: `app_metadata.role` → `user_metadata.role` → hardcoded fallback (`admin@stowaway.lk` → `superadmin`, else `staff`).

## Business Rules Worth Knowing
- **Airport/CMB cash lockout**: Any booking touching an airport location (`is_airport`, `requires_stripe`, `code === 'LOC_001'`, or id/code containing `"airport"`/`"cmb"`) is forced to `payment_method = stripe_simulated` (card) and cash is disallowed — enforced **server-side** in both `saveBooking` and `updateBookingPayment` regardless of what the client sends. Do not weaken this to a client-only check. Whether it's *paid* is now a separate, ledger-derived question (see the payments ledger rule below) — airport no longer force-sets `payment_status='paid'` at insert time, only the payment *method*.
- **Pricing is always recalculated server-side** in `POST /api/bookings` from live `item_tiers` rows; client-submitted totals are not trusted and booking creation fails closed if database pricing cannot be loaded.
- **Duration billing**: Elapsed time in whole 24-hour cycles; crossing a 24h boundary rounds up to the next whole day (see `pricing.ts` doc comment for exact examples).
- Insurance is a flat per-item fee (`insurance_fee_usd`) charged once per unit when `insuranceEnabled`, independent of duration.
- `booking_status` lifecycle: `confirmed` → `in_transit` → `deposited` → `picked_up` (or `cancelled`). Enforced server-side via `ALLOWED_TRANSITIONS` in `/api/staff/bookings/[id]`. Staff dashboard operates on a rolling window (`ops_window_hours`) of these. Each transition (and cancellation) sends the customer a status email — see the email rule below.
- **Bags don't leave with a balance still owed**: the same route refuses a transition *to* `picked_up` when `balanceDueUsd > 0` (409, checked server-side — not just a disabled button, so it can't be bypassed by calling the API directly). Applies to every caller of that endpoint (staff ops board, search results, admin's quick-status buttons). Collect the balance first via `CashCollectButton`/`PayLinkButton`, which are always visible alongside the status controls, then hand over. This does **not** apply to the `deposited` transition (receiving bags at drop-off) — only to release.
- **The payments ledger is the authority, not `bookings.payment_status`** (migration 007, `public.payments`). Every money movement — a cash collection or a settled Stripe charge — is one row (method, amount, status, who/which session). `BookingRecord.amountPaidUsd` and `.balanceDueUsd` are computed by summing succeeded ledger rows against `grandTotalUsd`; `.paymentStatus` (`pending`/`partially_paid`/`paid`/`failed`) is *derived* from that in `mapBooking()`, never read raw off the column. The `bookings.payment_status` column still exists and is kept in sync (so `.eq('payment_status', ...)` filters keep working), but treat it as a cache — if you ever need to know what's actually owed, read `balanceDueUsd`, don't hand-roll a "is this paid" check against the raw column.
- **Extensions/top-ups always charge the current balance, never a separate "delta" concept.** `markCashCollected()` and `POST /api/bookings/[id]/checkout` both operate on `balanceDueUsd` at the moment they're called — so the exact same function handles a booking's first payment, a post-extension top-up, or catching up a partial payment. Don't introduce a separate "extension payment" code path; if a new payment flow is needed, make it charge `balanceDueUsd` too.
- **Editing a booking's schedule re-prices it and re-derives the balance from the ledger**: `updateBookingDetails` (`db.ts`) recalculates the grand total from live locations/`item_tiers` when a drop-off/pick-up location or time changes, then re-syncs `payment_status` from `getBookingById()`'s freshly-derived value — it does not hand-set `'paid'`/`'pending'` itself. An edit is never blocked by payment status. If the new balance is > 0, the route sends a balance-due email (with a live Stripe pay link when configured). There is intentionally no separate "extension payment" record — see the ledger rule above.
- Item quantities/tiers on an existing booking are **not editable** anywhere yet (out of scope — would need a `booking_items` diff + re-pricing of a changed item list). If asked for this, it's a genuinely new feature, not an extension of `updateBookingDetails`.
- **There is no separate "airport handling fee."** It used to be a global flat fee (`app_settings.airport_service_fee_usd`) stacked on top of the airport location's own `dropoff_surcharge_usd`/`pickup_surcharge_usd` — double-charging every airport booking (the seeded airport location already carries a surcharge on both legs). Removed in migration 006; `calculateGrandTotal` no longer accepts an airport fee parameter at all. The airport cost lever is the location's own surcharge fields, full stop — don't reintroduce a second fee on top of them.
- **Flight number is its own column** (`bookings.flight_number`, migration 006), not stuffed into `notes`. The booking flow's "Arrival Flight Number (Preferred)" field (`book/page.tsx` — relabeled from "(Optional)" 2026-09 per client request; still optional in validation, the label just encourages providing it) posts `flightNumber` separately; `notes` is free text only. `BookingRecord.flightNumber` and `.notes` are both surfaced (and both editable via `BookingEditForm`) — don't collapse them back into one field.
- **Cash collection tracking**: `bookings.cash_collected_by` (→ `staff.user_id`) / `cash_collected_at` record who physically collected cash and when, set by `recordPayment()` whenever a `method: 'cash'` payment succeeds. Surfaced through `CashCollectButton` (`src/components/admin/CashCollectButton.tsx`, shared by `/staff` and `/admin`) — cash-only, renders nothing for card bookings, and its label/collected amount is always `balanceDueUsd`, not the full total. `cashCollectedByName` is stripped from every customer-facing response (`/api/bookings*`) alongside `passportNo` — it's internal staff identity, not the customer's business.
- **Card payments are real Stripe, gated by configuration, not simulated.** `isStripeConfigured()` (`src/lib/stripe.ts`) checks `STRIPE_SECRET_KEY`. When configured: every card payment goes through a Checkout Session (`createCheckoutSession`) + the webhook (`markStripePaymentSucceeded`/`Failed`) — nothing else marks a card payment paid. When *not* configured (local dev, or before the client has Stripe keys): `updateBookingPayment` settles it instantly via the ledger so the app stays fully usable without live keys. `PayLinkButton` (`src/components/admin/PayLinkButton.tsx`) is the staff-facing "pay at counter" action — generates a real Checkout Session for `balanceDueUsd` and shows it as a QR the customer scans with their own phone; nothing on that screen marks the booking paid, the webhook does. Since the charge settles on the *customer's* phone while staff are watching a QR on theirs, the modal polls `GET /api/staff/bookings/[id]` every 3s while open and flips to a "Paid" state the moment `balanceDueUsd` hits 0 — without that poll, staff would have no way to know the webhook landed short of closing the modal and refreshing manually. Don't add a "mark card payment collected" button that bypasses Stripe — that would defeat the point of using a real gateway.
- **Email is real, gated by configuration, never blocking.** `src/lib/email.ts`: Resend tried first, plain SMTP (nodemailer) as backup (works with any provider, including a shared-hosting mailbox) — configure via env vars, see `.env.example`. Every send attempt is logged to `public.email_log` (provider, status, error) so "did the customer get this" has an answer. Callers always fire-and-forget with `.catch(console.error)` — an email failure must never fail the booking/payment/status-change it's attached to. Triggers: `sendBookingConfirmedEmail` — **cash** bookings send it immediately in `POST /api/bookings` (there's no payment step, cash is collected in person later, so booking creation *is* the confirmation moment); **card** bookings deliberately do NOT send it at creation — nothing has been charged yet — instead it fires the first time that booking's card payment actually succeeds (fixed 2026-09, was a bug: it used to fire unconditionally at creation, so a card customer could get a "confirmed" email before paying, or before even reaching Stripe checkout). `sendPaymentReceivedEmail` fires for every *subsequent* successful payment (an extension/top-up, or any card payment after the first). Both `updateBookingPayment` (the dev-fallback instant-settle path, `db.ts`) and `markStripePaymentSucceeded` (the live Stripe webhook) decide which of the two to send by checking whether a succeeded payment already existed for that booking (`hasSucceededPayment()`) — first-ever payment on a card booking → `sendBookingConfirmedEmail`, every payment after that → `sendPaymentReceivedEmail`; a replayed webhook for an already-succeeded session sends neither. Cash's `markCashCollected` (`collect-cash` route) always sends `sendPaymentReceivedEmail` regardless of payment count, since cash bookings already got their confirmation at creation. Other triggers: a schedule edit leaves a balance due (`sendBalanceDueEmail`), and every staff status transition including cancellation (`sendStatusUpdateEmail`/`sendBookingCancelledEmail`). Templates live in `emailTemplates.ts` and link back to `/booking/[id]/confirmation` rather than embedding a QR image — that page already renders the live QR and current status.

## Email OTP Verification (`src/lib/otp.ts`, migration 008)
Client requirement, 2026-09: gate both booking creation and the `/my-bookings` lookup behind a 6-digit emailed code, replacing the old phone-only lookup (a phone number is knowable by someone other than the customer, so it was never a real credential — see the removed route's history in `bookings/route.ts`).

- **Two purposes, one mechanism**: `otp_verifications` (`purpose`: `'booking_create'` | `'booking_lookup'`), `code_hash` (HMAC-SHA256, keyed by `OTP_HMAC_SECRET` — the code itself is never stored), 10-minute expiry, 5-attempt lockout, 60s resend cooldown, single-use (`used_at`). Not the same table as the old unused `customers.otp_code`/`otp_expires_at` (migration 001, dropped in 008) — those were keyed to an existing customer row, but `booking_create` runs before a customer necessarily exists.
- **`booking_create`**: the customer types an email into `/book` step 4 → `POST /api/otp/request {contact: email, purpose: 'booking_create'}` sends a code directly to that address (no existing account to resolve against) → `POST /api/otp/verify` flips `verified_at` → `POST /api/bookings` must include the resulting `emailVerificationId`, and `consumeOtp()` re-checks verified/unused/within-20-minutes/email-matches before marking it `used_at` and proceeding. Changing the email client-side after verifying resets `otpStage` to `'idle'` (`book/page.tsx`) — the server-side email match check is the real guard, the client reset just avoids a misleading "Verified" badge next to an unverified address.
- **`booking_lookup`**: the customer types phone OR email on `/my-bookings` → `POST /api/otp/request {contact, purpose: 'booking_lookup'}` resolves it server-side to the matching customer's **on-file** email via `findCustomerByContact()` (`db.ts`) and sends there — **never to the raw typed value**, so this endpoint can't be used to relay a code to an address the requester doesn't already own on the account → verify → `GET /api/my-bookings?verificationId=...` re-validates and marks the verification used, then returns bookings for the resolved `customer_id`. Single-use by design: refreshing the results page requires a fresh code, in exchange for not needing any session/token layer at all.
- **No enumeration, by construction**: `requestOtp()` always returns a `requestId` and an identical generic message, whether or not a match was found or the request was rate-limited (a fabricated `blocked-*`/`no-match+*@invalid.local` path exists specifically so the HTTP layer never branches on whether a real send happened). Don't add a differential response ("no account found" vs "code sent") anywhere in this flow — that reintroduces exactly the enumeration gap this replaced.
- **Email is now required, not optional**: `customers.email` is `NOT NULL` (migration 008) and `createBookingSchema.email` dropped its `.optional()`. `bookingEditSchema.email` can no longer be cleared to `''` either (staff-side edit) — same constraint, same reasoning. If a booking/customer somehow has no email, `/my-bookings` cannot resolve them and self-service lookup is a dead end for that customer — direct them to WhatsApp/call support rather than reintroducing a phone-only fallback for this case.
- **Known limitation, accepted**: rate limiting here reuses the existing in-memory `rateLimit()` (`src/lib/security/rateLimit.ts`), which doesn't share state across Vercel serverless instances — the per-code 5-attempt lockout (enforced in the database, not memory) is the real brute-force guard; the IP/email send-rate limits are a softer abuse brake on top, consistent with the rest of the app's rate limiting. Worth revisiting with a DB-backed counter if abuse is observed.
- **`OTP_HMAC_SECRET`** (required): a random 32+ byte secret, see `.env.example`. Rotating it invalidates every code currently in flight — don't rotate casually.

## Database Schema (Supabase)
Migrations live in `supabase/migrations/` (`001_schema.sql`, `002_add_insurance_hourly_slots.sql`, `003_public_inserts.sql`, `004_security_settings_ops.sql`, `005_item_tier_images.sql`, `006_flight_number_cash_tracking_and_airport_fee_cleanup.sql`, `007_payments_ledger_and_email_log.sql`, `008_email_otp_verification.sql`, `009_landing_page_content_settings.sql`, `010_location_direction_display_names.sql`) — this is the historical, step-by-step record; keep it as-is. `src/lib/supabase/types.ts` is the authoritative TS shape. Migrations are append-only history — a later migration undoes an earlier one (006 drops what 001/002/004 added) rather than editing those files in place.

**For actually standing up a database, use the consolidated files instead of the migration folder** — same end state, one paste each instead of eight:
- `supabase/schema.sql` — every table/trigger/index/RLS policy from 001–008, concatenated in order. Deliberately excludes two files that used to exist and are now deleted from the repo entirely: `fix_admin_rls.sql` (re-opened the public/authenticated write access that migration 004 locked down; audited — nothing in `src/components` queries Supabase directly, every write goes through `src/lib/db.ts` server-side, so that file served no purpose and was pure attack surface) and `fix_auth_passwords.sql` (its logic is now done correctly, idempotently, and without a hardcoded plaintext password by `seed_accounts.sql` below). Do not recreate either — if a future admin/staff feature genuinely needs a scoped RLS policy for a client-side query, write a new one reviewed on its own merits.
- `supabase/seed_catalog.sql` — real business config: locations, time slots, item tiers, add-on services. Required for the booking flow to function at all. Edit the values before running, or run as-is and change everything later via `/admin`.
- `supabase/seed_accounts.sql` — creates the admin (`superadmin`) and staff Supabase Auth accounts, plus their `public.staff` rows and the `auth.identities` row `signInWithPassword` requires (missing it causes a 500, not a clean "invalid password"). Also explicitly sets `confirmation_token`/`recovery_token`/`email_change_token_new`/`email_change`/`email_change_token_current`/`phone_change`/`phone_change_token` to `''` rather than leaving them `NULL` — GoTrue scans these into non-nullable Go string fields on password login and returns a bare 500 (not a clean "invalid credentials") if any are `NULL`, which a raw `INSERT` into `auth.users` otherwise leaves them as. Caught once already in production (2026-09) — don't drop these columns from the `INSERT`/`UPDATE` statements. Ships with placeholder passwords (`CHANGE_ME_ADMIN_PASSWORD` / `CHANGE_ME_STAFF_PASSWORD`) you must replace locally before running — never commit real passwords into this file, they'd sit in git history permanently even after rotation.
- `supabase/seed_demo_data.sql` — fake customers/bookings for local dev/testing. Never run against the client's production database.
- `supabase/cleanup_for_handoff.sql` — wipes bookings/customers/payments/audit/email log and, in its default (full) form, the catalog and `app_settings` too — everything except your admin/staff login (`auth.users`/`auth.identities`/`public.staff` are untouched). Use this to hand the client a clean, working instance without losing your own access to it. Has a commented-out "PARTIAL CLEANUP" variant at the bottom that keeps the catalog and only clears test bookings/customers — normally the better choice once the client's real locations/pricing are already seeded.
- The old single `supabase/seed.sql`, plus the ad-hoc `fix_admin_rls.sql`/`fix_auth_passwords.sql` patches, have been deleted — don't recreate them, use the files above.

- `public.locations`: Dropoff/pickup points. Flags: `is_airport`, `requires_stripe`, `allows_cash`, plus `dropoff_surcharge_usd` / `pickup_surcharge_usd` — the only airport-cost lever, see Business Rules above. `dropoff_display_name` / `pickup_display_name` (migration 010, both nullable, admin-editable under Locations) let the same physical site read differently per direction in the booking flow's location picker (e.g. "CMB Airport Drop Off Location" vs "CMB Airport Pickup Location") — `LegPicker` in `LocationSelector.tsx` falls back to the base `name` when either is unset. This is deliberately NOT two separate location rows: that would let a pickup-only label wrongly appear as a selectable drop-off option, and would split one site's surcharge/hours/flags across two rows. Every other surface (staff/admin, emails, `PriceSummaryPanel`) still shows the base `name` — the direction-specific label is scoped to the picker cards only, where the client explicitly asked for it.
- `public.time_slots`: Admin-configurable operational windows (`slot_type`: `window`|`hourly`, `day_of_week`, optional `specific_date` override).
- `public.item_tiers`: Pricing catalog — `rate_daily_usd`, `rate_weekly_usd` (post-7-day rate), `insurance_fee_usd`, `image_url`, `display_order`.
- `public.addon_services`: Additional paid services (e.g. airport delivery), `fee_usd`. **Not currently wired into the booking flow or pricing** — admin can manage the catalog but customers never see/select an add-on and it's never billed. Flag this to the client before building on top of it; it may be vestigial.
- `public.customers`: Verified customer profiles (`phone`, `full_name`, `email` — `NOT NULL` since migration 008, `passport_number`). The old `otp_code`/`otp_expires_at` columns (migration 001, never wired up) were dropped in 008 in favor of `public.otp_verifications`.
- `public.otp_verifications` (migration 008): email OTP codes gating booking creation and `/my-bookings` — see Email OTP Verification above. `code_hash` only, never the raw code. Service-role only.
- `public.bookings`: Main reservation table — FKs to `customers`/`locations`, computed totals, `payment_method` (`cash`|`stripe_simulated`), `payment_status` (**cache, not authority** — see Business Rules), `booking_status`, `qr_code_token`, `duration_days`, `insurance_enabled`, `idempotency_key`, `flight_number`, `cash_collected_by`/`cash_collected_at` (migration 006).
- `public.payments` (migration 007): **the payments authority.** One row per money movement — `booking_id`, `amount_usd`, `method` (`cash`|`stripe`), `status` (`pending`|`succeeded`|`failed`|`refunded`), `stripe_session_id`/`stripe_payment_intent_id` (unique, so a webhook retry can't double-record a charge), `collected_by` (cash only). Written exclusively by `recordPayment()`/`createPendingStripePayment()`/`markStripePaymentSucceeded()`/`markStripePaymentFailed()` in `db.ts` — never insert into this table anywhere else.
- `public.email_log` (migration 007): delivery record for every transactional email attempt (`booking_id`, `template`, `provider`, `status`, `error`). A log, not a queue — writes happen inline with `sendEmail()`, best-effort.
- `public.booking_items`: Line items per booking (tier + quantity + rate snapshot).
- `public.booking_addons`: Addon selections per booking.
- `public.staff`: Portal users — `role` (`staff`|`superadmin`) linked to Supabase Auth `user_id`. `bookings.cash_collected_by` and `payments.collected_by` reference `staff.user_id` (not `auth.users.id` directly) so PostgREST can embed the collecting staff member's name in one query.
- `public.app_settings`: Dynamic business configuration (insurance, pricing rules, limits, contact numbers). No longer includes `airport_service_fee_usd` (removed in 006).
- `public.audit_log`: INSERT/UPDATE/DELETE trail with actor, summary, old/new values, surfaced in the admin panel.

## Deployment Instructions
1. In the Supabase SQL Editor, run in order: `supabase/schema.sql`, then `supabase/seed_catalog.sql`, then `supabase/seed_accounts.sql` (fill in real passwords first — see the warning at the top of that file). Optionally `supabase/seed_demo_data.sql` for a dev/test database only. (Equivalent to running `supabase/migrations/001` through `007` individually — see Database Schema above for why the consolidated files are preferred.)
2. Deploy to Vercel with environment variables (full reference: `.env.example`):
   - `NEXT_PUBLIC_SUPABASE_URL`
   - `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (or `NEXT_PUBLIC_SUPABASE_ANON_KEY`)
   - `SUPABASE_SERVICE_ROLE_KEY` — value from Supabase Project Settings > API Keys. Supabase renamed this key type: the dashboard now shows it under the "Publishable and secret API keys" tab as the **secret key** (`sb_secret_...`), replacing the legacy JWT-style `service_role` key from the "Legacy API Keys" tab. Either works and both go in this same env var (the app just passes it straight to the Supabase client) — prefer the new `sb_secret_...` value for anything set up from now on; legacy keys are slated for deprecation by end of 2026.
   - `OTP_HMAC_SECRET` — **required**, not optional. A random 32+ byte secret (`node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`). Without it, email verification (booking creation + `/my-bookings`) is down entirely — see Email OTP Verification above.
   - `NEXT_PUBLIC_USD_TO_LKR` (optional fallback exchange rate; live rate is served by `/api/exchange-rate`)
   - `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` (optional, for Cloudflare Turnstile bot verification)
   - `NEXT_PUBLIC_SITE_URL` (canonical production origin — used by `sitemap.ts`/`robots.ts`/`metadataBase`; falls back to a placeholder domain if unset)
   - `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` (real card payments — see Business Rules; the app runs fine without these, card payments just settle via the dev fallback instead of a live gateway)
   - `RESEND_API_KEY` and/or `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`, plus `EMAIL_FROM` (transactional email — without either, sends are logged as failed and nothing else breaks)
3. In the Stripe dashboard, add a webhook endpoint at `{your domain}/api/stripe/webhook` subscribed to `checkout.session.completed`, `checkout.session.expired`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, and copy its signing secret into `STRIPE_WEBHOOK_SECRET`.

## Staff/Admin booking tools
- **Universal search**: both `/staff` (search box on the operations board) and `/admin` (`BookingsPanel`) can find any booking by phone/name/email/passport/reference regardless of status or booking date — `searchAllBookings()` / the widened `listBookings()` filter in `db.ts`. The staff operations board's default (no-search) view stays scoped to the rolling ops window; typing a query switches it to the flat, unscoped result list.
- **QR scan-to-lookup**: `src/components/staff/QrScanner.tsx` (camera + `jsQR`, no other scanning deps) decodes the confirmation page's existing QR — which already encodes `{origin}/booking/{id}` — and feeds the id into the same search box on both `/staff` and `/admin`. Needs `Permissions-Policy: camera=(self)` in `next.config.ts`; don't revert that to `camera=()`, it silently breaks the scanner (caught once already — the policy was blocking the app's own camera use, not just third parties).
- **Booking edit**: `BookingEditForm` (`src/components/admin/BookingEditForm.tsx`) is shared by both dashboards, and is wired into all three places a booking can be viewed — the staff ops-window task card, the staff search-result card, and the admin booking row. If a new booking-viewing surface is added, wire the edit form into it too rather than leaving it view-only; that gap (ops window had it, search results didn't at first) was a real bug already caught once.
- **Booking reference display**: always show `bookingRef(id)` (`src/lib/format.ts` — short `#XXXXXX` form) to staff/admin, never the raw UUID — nobody reads a UUID over the phone. Put the full id in a `title` tooltip if it needs to stay available, don't just print it. Status-change toasts also name the customer (`"{name} ({ref}) marked as X"`), not just the reference — a bare reference in a toast doesn't let staff sanity-check they acted on the right person.
- **Cash collection tracking**: `CashCollectButton` (`src/components/admin/CashCollectButton.tsx`) is shared by both dashboards and wired into every place a cash booking can be viewed (admin booking row, staff task card, staff search result). Cash-only — it renders nothing for card bookings. Uses `PATCH /api/staff/bookings/[id]/collect-cash` → `markCashCollected()` in `db.ts`. See Business Rules above for the data model.
- **Card pay-at-counter**: `PayLinkButton` (`src/components/admin/PayLinkButton.tsx`) is wired in next to `CashCollectButton` everywhere it appears — card-only, renders nothing for cash bookings, nothing for a fully-paid booking. Generates a real Stripe Checkout Session for `balanceDueUsd` and shows it as a scannable QR; the booking updates on its own once the webhook confirms the charge, nothing here marks it paid directly.
- **Admin Payments panel** (`src/components/admin/PaymentsPanel.tsx`, `/admin` → Day to day → Payments): the financial view — every ledger entry (cash + card) with today/week/all-time totals, filterable by method/status. Read-only by design; the ledger is written exclusively by `db.ts`'s payment functions, never edited here.
- **The booking flow's "Arrival Flight Number" field has its own column** (`bookings.flight_number`, migration 006) and its own `flightNumber` state in `book/page.tsx` — it used to be stuffed into the generic `notes` column, which is fixed now (see Business Rules above). Don't reintroduce that overload.
- **Step 4's name field is First Name + Last Name, not one input** (2026-09, client request) — `book/page.tsx` holds separate `firstName`/`lastName` state and derives `fullName = \`${firstName} ${lastName}\`.trim()` locally; the API payload, `customers.full_name` column, and every downstream reader (staff/admin, emails, `BookingEditForm`) are unchanged and still deal in a single full-name string. Don't add `first_name`/`last_name` columns without a real reason — splitting storage would ripple across every existing display/export and gain nothing the derived string doesn't already give the booking form.
- **Insurance's dollar amount lives on the item tier** (`item_tiers.insurance_fee_usd`, edited under Item Tiers), not in Business Settings — Settings only has the on/off switch and the label text. The Settings panel's Insurance section explicitly cross-references this; keep that pointer if the copy changes, it's a real spot people look and don't find it.

## Security audit notes (last pass)
- `npm audit` was clean (0 vulnerabilities) after bumping `next` 16.2.11 → 16.3.3 (same major, no breaking changes) — re-run `npm audit` periodically, the previous 6 high-severity advisories were all transitively from `next`'s bundled `postcss`/`sharp`.
